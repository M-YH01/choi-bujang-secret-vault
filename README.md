# BYTE BACK 방어전 시작 틀 R5

이 저장소는 1단계에서 학생 본인이 GitHub 저장소와 Vercel 배포를 만드는 출발점입니다. 시작 틀에 들어 있던 메모 네 건은 가상 자료이며, 2단계부터는 저장소가 아니라 Supabase에 둡니다. 실제 학생 자료, 토큰, 비밀키를 넣지 마세요.

## 학생이 하는 일: 세 걸음

1. GitHub 계정을 만듭니다.
2. 방어전 1단계 카드의 **Deploy** 버튼을 누릅니다. Vercel에 GitHub로 로그인하고, 새 저장소가 **본인 계정의 Public 저장소**인지 확인한 뒤 Deploy를 누릅니다.
3. 배포가 끝나면 화면에 나온 `https://…vercel.app` 주소를 방어전 1단계 카드에 붙여넣고 제출합니다. 저장소 주소나 설정 파일은 적지 않습니다.

배포가 끝나면 `/`에서 점령된 가상 자료실을 볼 수 있습니다. 시작 틀에서는 `/data.json`에 같은 가상 메모가 공개되어 있었고, 이 공개 상태를 확인하는 것이 1단계의 출발점이었습니다. 이 저장소는 2단계 작업으로 메모를 `/data.json`에서 빼고 서버 함수로 읽게 바꿨고, 3단계에서 로그인한 사람만 읽고 고치게, 4단계에서 로그인해도 본인 메모만 다루게, 5단계에서 자료 요청을 서버 함수 한곳으로 모으게, 6단계에서 판정기에 기기 등록 규칙을, 7단계에서 평소와 다른 접속은 다시 확인하는 규칙을, 8단계에서 자료를 구역으로 나누는 규칙을, 9단계에서 조회 폭주를 찾아 회수를 제안하는 탐지 규칙을, 10단계에서 검증된 정책 사본과 비교·복원하는 도구와 메모 한 건 복원 경로를 더했습니다(바로 아래 참고). 1단계 접수와 심판 판정은 포털에서 확인합니다.

## 10단계: 백업에서 자료실을 되살림 (현재 작동하는 기능)

### 제작 1: 검증된 사본과 지금 시험 정책의 차이 (`npm run policy:diff`)

- "시험 정책"은 `src/decider.mjs`, `src/detect.mjs`, `aleph.config.json`의 `allowedRoutes` 값 하나입니다. **실제 운영 정책은 읽지도 바꾸지도 않습니다.**
- 사본은 `policy/verified-policy.json`입니다. 9단계까지 정상 작동을 확인한 상태에서 `npm run policy:snapshot`으로 만들었고, 두 코드 파일의 전문과 해시, 허용 경로, 규칙 이름, 고정 가상 요청 12개의 결과(요약값 포함)가 들어 있습니다. 메모 본문·이메일·토큰은 없습니다.
- `policy:diff`는 먼저 사본을 검증합니다: 형식, 파일 해시, 요약값, 그리고 **사본 안의 코드를 임시 폴더에서 실제로 실행해 기록된 결과를 다시 만들 수 있는지**. 사본이 없거나 검증이 실패하면 **비교하지 않고 중단**합니다(종료 코드 1).
- 통과하면 **다른 점만** 보여 줍니다(코드 파일, 지금만/사본에만 있는 허용 경로·규칙, 결과가 달라진 가상 요청). 차이가 있으면 종료 코드 2, 같으면 0입니다.

### 제작 2: 시험 정책을 사본 버전으로 되돌리기 (`npm run policy:restore`)

1. `npm run policy:restore` — 되돌릴 내용만 보여 주고 **아무것도 바꾸지 않습니다**.
2. 내용을 확인했다면 `npm run policy:restore -- --apply --confirm <사본 버전>` — 버전을 정확히 적어야만 실행됩니다.
- 쓰는 곳은 두 코드 파일과 `allowedRoutes` 키뿐입니다. `aleph.config.json`의 다른 값(단계, 주소 등)은 그대로입니다. 지우거나 `git reset`을 쓰지 않습니다.
- 끝나면 다시 계산해 사본과 같은지 확인하고, `policy/audit.log`에 한 줄을 **덧붙입니다**(이전 줄은 건드리지 않음, 파일 해시만 기록). 확인이 실패하면 오류로 끝냅니다.
- 되돌린 뒤에도 B 계정이 A의 자료를 요청하면 거부(구역 규칙·소유자 재대조), A의 정상 요청은 허용되는 것을 가상 요청 결과(`policy:diff` 차이 없음)와 자료 API 시험으로 확인합니다.

### 제작 3: 비공개 백업에서 메모 한 건 복원 (`POST /api/restore/notes/:id`)

- 서비스: `src/restore-api.mjs`, 경로 파일 `api/restore/notes/[id].js`. `aleph.config.json`에 `restoreRoute`로 적었고, 배포가 공개하는 `/aleph.json`과 제출 묶음에 이 경로가 실립니다. `allowedRoutes`에도 `POST /api/restore/notes/:id`를 적었습니다(제출한 경로 목록에서 복구 경로를 찾을 수 있게). 판정기(`src/decider.mjs`)의 구역 규칙은 바꾸지 않아, 판정기가 이 경로를 실제 요청에 적용한다면 기본값대로 거부합니다. 이 연결은 확인하지 못했습니다.
- 백업 표: `study_notes_backup`(비공개, 서버 비밀 키로만 읽음), 감사 표: `study_notes_audit`(추가만, 수정·삭제 권한 회수). 만드는 SQL은 `sql/10-backup-tables.sql`이며, **침해 전에** Supabase SQL Editor에서 실행해야 사본이 의미가 있습니다.
- 사본 자동 만들기: `sql/10-auto-backup-trigger.sql`을 실행하면 메모가 **새로 만들어질 때** 처음 모습이 사본 표에 자동으로 들어갑니다. 이미 사본이 있는 메모는 덮어쓰지 않아 변조된 내용이 사본이 되지 않고, 삭제·수정에는 반응하지 않습니다. 사본 저장이 실패해도 메모 저장은 막지 않고 감사 표에 `auto_backup failed`를 남깁니다. 이 SQL과 `10-backup-tables.sql`의 해시식은 임시 로컬 Postgres 16에서 실행해, SQL 해시가 `contentSha256`(JS)와 같고 변조가 사본을 덮어쓰지 않음을 확인했습니다. 실제 Supabase에서는 아직 실행해 보지 않았습니다.
- 한 건만 복원합니다. 확인 순서: 로그인 확인 → `:id`가 UUID → 백업의 `id`·`owner_id`가 로그인한 사람과 같음(없거나 남의 것이면 같은 404) → 백업 해시 재계산(`sha256(제목 + 0x00 + 본문)`)이 저장된 해시와 같음(다르면 422, 쓰기 없음) → 현재 행의 주인이 다르면 409.
- 이미 같으면 아무것도 쓰지 않습니다. 감사 `started` 기록이 실패하면 쓰기 전에 멈춥니다. 쓴 뒤 다시 읽어 해시를 대조하고 `restored`를 기록합니다. 본문은 응답·로그·감사에 넣지 않습니다. 다른 메모와 다른 사람의 행은 건드리지 않습니다.
- 메모 번호는 경로의 `:id`를 우선 쓰고, 번호 없는 주소 `POST /api/restore/notes`로 부르면 본문의 `id`(또는 `noteId`)에서 읽습니다. 로그인·소유자·해시 검사는 두 방식 모두 같고, 번호가 없거나 UUID가 아니거나 남의 것이면 같은 404입니다.
- 본문 `{"dryRun": true}`를 보내면 쓰지 않고 "복원될 것인가"만 답합니다.
- 성공 응답에는 사본 검증 결과(`backupVerified`, `backupVersion`)와 바뀔 항목의 이름(`changes`: `title`·`content`·`row_missing`)만 들어갑니다. 해시가 맞지 않으면 422와 `backupVerified: false`입니다. 제목·본문은 응답에 넣지 않습니다.

### 제작 4: 복구 뒤 1~9단계 다시 확인하는 순서

각 줄은 정상 결과와 거부되어야 할 결과입니다. **자동**은 이 저장소에서 `npm run check:all`로 확인하는 가상 시험이고, **직접**은 배포 주소에 학생이 해 봐야 하는 것으로 아직 실행하지 않았으면 **미실행**입니다.

1. (자동) `npm run check:all` — 단위 시험, 판정기·탐지 연습, 빌드. 실제 심판 판정이 아닙니다.
2. (자동) `npm run policy:diff` — 차이 없음이면 정책이 사본과 같음.
3. 1단계: 배포 주소 `/data.json`에 가상 메모 문구가 보이지 않음 — 직접, 미실행.
4. 2~3단계: 로그인 없이 `/api/notes` → 401 거부 / A로 로그인해 목록·추가 → 정상 — 직접, 미실행.
5. 4단계: A의 토큰으로 A의 메모 읽기 → 200 / B의 토큰으로 A의 메모 번호 읽기·수정·삭제 → 404 거부 — 직접, 미실행.
6. 5단계: 공개 키로 원본 주소(Supabase) 직접 읽기 → 거부 — `npm run bundle`의 점검이 대신 보내며, 이 저장소에서는 네트워크가 없어 미실행.
7. 6~8단계: `npm run decider:test` — 등록 기기 허용, 미등록 기기·강사 영역·허용 밖 메서드 거부, 복합 이상은 재확인 — 자동(가상 요청).
8. 9단계: `npm run detect:test` — 120건 관찰, 121건 회수 제안 — 자동(가상 사건).
9. 10단계: B 계정으로 `dryRun` 요청 → `wouldRestore` / A 메모 번호를 B가 복원 요청 → 404 거부 / 로그인 없이 → 401 거부 — 직접, 미실행.

### 10단계의 알려진 약점과 확인하지 못한 것

- SQL의 해시 계산식과 감사 표 권한 회수가 실제 Supabase에서 의도대로 동작하는지는 아직 실행하지 않았습니다. 복원 API의 해시 대조가 첫 자체 점검입니다.
- 사본(`policy/verified-policy.json`)은 Git 안에 있어서, 저장소를 고칠 수 있는 공격자가 사본까지 바꾸면 검증을 통과합니다. 요약값(`version`)을 저장소 밖(수업 포털 메모 등)에 따로 적어 두면 이 약점을 줄입니다.
- 백업 표도 같은 Supabase 프로젝트에 있어 프로젝트 전체가 침해되면 함께 위험합니다. 별도 보관은 하지 않았습니다.
- 판정기와 실제 운영 엔진의 연결, 복원 경로를 심판이 어떻게 보는지는 확인하지 못했습니다.

## 9단계: 도플갱어를 찾고 권한을 거둠 (10단계의 바탕)

### 탐지 규칙 (`src/detect.mjs`)

`detect(events)`에 규칙 `burst_read` 하나를 넣었습니다. 사건 모양과 돌려줄 값은 `docs/DETECT_EVENTS.md` 그대로입니다.

- **의심 조건**: 같은 `identity.sub`의 `GET` 사건이 어느 10분 구간에서든 **120건을 넘으면**(121건 이상) 의심입니다. 정확히 120건은 의심이 아닙니다.
- **10분 구간**: 첫 사건과 마지막 사건의 시각 차가 10분(600초) **이하**이면 같은 구간입니다. 정확히 600초 간격은 같은 구간으로 세고, 1초라도 넘으면 다른 구간입니다. 문서가 경계를 정하지 않아 이 저장소가 고른 기준입니다. 창 계산은 `at` 시각만 쓰고, 입력 순서가 뒤섞여 있어도 시각순으로 정렬해 계산합니다.
- **합치지 않는 것**: 다른 사용자의 사건, 10분 밖의 사건, `GET`이 아닌 사건(`POST` 등)은 세지 않습니다.
- **결과**: 의심이면 정확히 `{ action: 'propose_revocation', reasonCode: 'burst_read', subject: <그 sub> }` 세 키만, 아니면 `{ action: 'observe' }`만 돌려줍니다. 기기 번호 등 다른 키는 덧붙이지 않습니다. 의심 사용자가 둘 이상이면 가장 먼저 한도를 넘은 사용자 한 명(같은 시각이면 `sub` 순서)입니다.
- **입력 처리(제작 1)**: 사건마다 `at`(시각), `method`(요청 종류), `identity.sub`(가명 사용자) **세 값만** 읽습니다. 네트워크·기기·지역·헤더·메모 내용·토큰은 읽지도 저장하지도 출력하지도 않고, 사건에 그런 값이 붙어 있어도 결과에 영향을 주지 않습니다. 세 값이 모두 올바르지 않은 사건(시각을 읽을 수 없음, 메서드가 정확히 `GET`이 아님, `sub`가 비었거나 128자 초과 등)은 정상값으로 채우지 않고 건너뜁니다. 배열이 아닌 입력은 시작 틀처럼 `TypeError('invalid_detection_events')`입니다.
- 이 함수는 회수를 **제안만** 합니다. 회수 API를 만들거나 부르지 않았고, 기기 권한도 바꾸지 않았습니다. 판정기(`src/decider.mjs`)의 허용/거부 응답 형식은 바꾸지 않았습니다.

### 확인 순서

1. `npm run detect:test` — 정상 출력은 아래 여섯 줄이 모두 `통과`입니다.
   - 정상 조회 30건, 10분 안에 120건, 서로 다른 사용자 각 100건, 10분 밖으로 흩어진 조회 200건 → `observe`
   - 10분 안에 121건, 폭주 조회 200건 → `propose_revocation`·`burst_read`
2. `npm run test:detect` — 120건/121건 경계, 600초/601초 경계, 구간이 뒤쪽에 있는 폭주, 사용자 섞임, `GET`이 아닌 사건, 뒤섞인 순서, 모양이 틀린 사건 건너뛰기, 세 값만 읽는지, 결과 키가 세 개뿐인지, 입력을 바꾸지 않는지를 확인합니다.

이 두 명령은 가상 사건 연습이며 **실제 접속 회수나 심판 판정의 증거가 아닙니다.**

### 9단계의 알려진 약점과 확인하지 못한 것

- **운영 반 엔진이 검증한 사건을 이 함수에 전달하고, 회수 제안을 집행해 접속을 거두는 경로가 연결돼 있는지는 확인하지 못했습니다.** `detect:test`가 통과해도 실제 접속 차단이나 권한 회수가 동작한다는 뜻이 아닙니다. 이 저장소는 사건을 모으지도, 회수를 실행하지도 않습니다.
- 기준값(10분에 120건 초과)은 과제 계약의 값입니다. 사용자별로만 세므로, 공격자가 계정을 여러 개 쓰거나 속도를 한도 아래로 맞추면(10분에 120건 이하) 이 규칙을 피할 수 있습니다. `GET`만 세므로 쓰기 폭주는 보지 않습니다.
- 시각 경계(정확히 600초)를 포함으로 한 선택이 심판의 기준과 다를 수 있습니다.
- 사건을 저장하지 않고 호출마다 받은 배열만 계산합니다. 이전 호출의 사건과는 합치지 않습니다.
- 5~8단계까지의 약점(서버 전용 키가 RLS를 우회하고 소유자 검사 코드가 방어선인 점, 호출 횟수 제한 없음, 화면이 실행 중 공개 키를 읽음, 판정기와 실제 접속 경로의 연결 미확인, 8단계의 서비스 이름·이유 코드 가정)은 그대로입니다.

## 8단계: 자료마다 갈 수 있는 구역을 나눔 (9단계의 바탕)

### 구역과 자원 ID (제작 1)

- 자료를 세 구역으로 나눕니다: 메모(`note`), 반 공지(`notice`), 강사 자료(`instructor`). `src/resources.mjs`가 `구역:번호` 모양의 **자원 ID**(`note:<메모 번호>` 등)를 만들고 읽습니다. 구역 이름과 번호 모양이 맞지 않으면 만들지 않습니다.
- 메모 한 건 API(`/api/notes/:id`)의 성공 응답에는 `X-Resource-Id: note:<번호>` 헤더가 붙습니다(거부 응답에는 붙지 않습니다). 응답 본문(`{id,title,body}`)과 기존 주소는 바꾸지 않았고, 화면 메뉴도 바꾸지 않았습니다.
- 반 공지와 강사 자료는 **이 저장소에 자료와 API가 없습니다.** 자원 ID 모양만 정의했습니다.

### 판정기 구역 규칙 (제작 2)

`src/decider.mjs`에 규칙 `resource_zone`을 더했습니다. `RULE_IDS`는 `['device_registered', 'resource_zone', 'step_up_required']`이고, 판정은 기기 규칙 → 구역 규칙 → 재확인 규칙 순서입니다(허용되지 않는 경로는 복합 이상 접속이어도 재확인이 아니라 거부입니다). 허용 목록에 없으면 모두 `deny`·`resource_not_allowed`입니다.

| 서비스 | 허용 | 거부 |
|---|---|---|
| `notes` (메모) | `GET`·`PUT`·`DELETE /notes/:id` (자료 ID 하나를 고르는 경로만) | 전체 목록 `GET /notes`, 추가 `POST /notes`, 그 밖의 메서드 |
| `announcements` (반 공지) | `GET /announcements`, `GET /announcements/:id` | `POST`·`PUT`·`PATCH`·`DELETE` 전부 (누구에게나) |
| `instructor` (강사 자료) | 없음 | 전부 |
| 그 밖의 서비스·경로 | 없음 | 전부 |

- 경로는 `route`의 모양(`GET /notes/:id`)과 실제 `path`(`/notes/<번호>`)가 서로 일치하고, `service`·`method`도 같을 때만 인정합니다. `/api` 접두사가 붙은 모양(`GET /api/notes/:id`)도 같은 규칙으로 읽습니다.
- 메모 번호는 UUID로 좁히지 않습니다(심판의 가상 요청 번호는 UUID가 아닐 수 있음). 다만 한 구간이어야 하고 `.`, `..`, 빈 값, 128자 초과, 공백·제어 문자·`?`·`#`·`\`, 인코딩된 슬래시(`%2F`, `%5C`)는 거부합니다.
- 쿼리(`queryLength`, `querySha256`)는 읽지 않아 쿼리로 기능을 고를 수 없습니다. `:id`와 같은 깊이에 `export` 같은 기능 경로를 두지 않았고, `GET /notes/export`처럼 route에 글자가 박힌 경로는 허용 목록에 없어 거부됩니다.
- 판정기는 사용자 역할이 요청에 없으므로 `role`·`identity`·`device`·`geo`를 읽지 않습니다. **메모 주인 비교는 판정기가 아니라 아래 API가 합니다.** 강사의 공지 수정은 판정기가 아니라 서버의 관리 경로에서 처리해야 하는데, 그 관리 경로와 강사 권한 저장소는 이 저장소에 **아직 없습니다(미구현)**.
- `aleph.config.json`의 `allowedRoutes`는 판정기가 허용하고 이 서버가 실제로 제공하는 경로만 메서드를 붙여 적었습니다: `GET /api/notes/:id`, `PUT /api/notes/:id`, `DELETE /api/notes/:id`. 반 공지 읽기는 판정기가 허용하지만 이 서버에는 공지 API가 없어 적지 않았습니다. `step`은 8입니다. 8단계부터 배포 정보(`scripts/deployment-identity.mjs`)는 메서드 없는 경로를 받지 않습니다.

### 자료 API의 소유자 재대조 (제작 3)

`src/notes-api.mjs`의 한 건 경로(GET·PUT·DELETE)는 두 번 확인합니다.
1. DB에 **저장된 소유자(`owner_id`)만** 따로 조회해 서버가 검증한 사용자 ID와 대조합니다(제목·내용은 읽지 않음). 남의 메모, 주인 없는 메모, 없는 번호는 모두 같은 `404 NOT_FOUND`입니다.
2. 통과해도 읽기·수정·삭제 질의에 다시 `owner_id = 내 ID` 조건을 붙이고, 수정할 때 새 행의 `owner_id`도 본인으로 고정합니다.

- 요청 본문·헤더·화면 메뉴의 `role`은 읽지 않습니다. 이 DB에는 저장된 강사 권한이 없어서 강사 경로는 만들지 않았습니다. 메뉴를 우회한 직접 API 요청에서도 다른 사람의 메모는 나오지 않습니다(시험으로 확인).
- 거부 사유는 서버 로그에 구역과 짧은 코드만 남깁니다: `notes_denied note not_owner`(남의 메모 또는 주인 없는 메모) / `notes_denied note not_found`(없는 번호). 번호·토큰·본문은 남기지 않습니다.

### 확인 순서

1. `npm run decider:test` — 가상 요청 네 건이 모두 `통과`여야 합니다(기기·재확인 연습). 이 명령은 구역 규칙을 직접 보여 주지 않습니다.
2. `npm run test:decider` — 자기 메모 한 건 읽기·수정·삭제 허용, 전체 목록·추가 거부, 공지 쓰기 거부, 강사 자료와 알 수 없는 경로 거부, 번호·경로 모양 변형 거부, 기기 규칙과 재확인 규칙과의 순서를 확인합니다.
3. `npm run test:notes` — 다른 사용자·주인 없는 행·꾸며 낸 역할 요청이 모두 404인지, 거부 로그에 번호·토큰이 없는지, 자원 ID 헤더를 확인합니다.
4. 배포 뒤 화면에서 A와 B 창을 따로 열어 각자 자기 메모만 읽고 고치는지 직접 확인합니다.

이 명령들은 가상 요청과 가짜 저장소로 한 연습이며 **심판 판정이나 운영 반 엔진의 결과가 아닙니다.**

### 8단계의 알려진 약점과 확인하지 못한 것

- **서비스 이름 `announcements`·`instructor`와 거부 이유 코드 `resource_not_allowed`는 계약(`docs/DECIDER_REQUEST.md`)에 정의돼 있지 않아 이 저장소가 정한 값입니다.** 운영 등록부의 `allowedReasonCodes`에 이 코드가 있는지, 심판이 같은 서비스 이름을 쓰는지 확인하지 못했습니다. 이름이 다르면 반 공지 읽기가 거부로 나올 수 있습니다(그 밖의 거부 동작은 영향이 없습니다).
- **판정기가 이 서버의 실제 요청 경로에 연결돼 있는지는 확인하지 못했습니다.** 만약 운영 엔진이 `allowedRoutes`와 판정기를 실제 요청에 적용한다면, 전체 목록(`GET /api/notes`)과 추가(`POST /api/notes`)가 거부돼 **화면의 메모 목록·추가가 막힐 수 있습니다.** 이 서버 코드는 두 경로를 계속 제공하지만 `allowedRoutes`에는 적지 않았습니다. 배포 뒤 A 화면에서 목록과 추가가 되는지 직접 확인해야 합니다.
- 강사 권한(관리 경로)과 반 공지 API는 만들지 않았습니다. 강사가 공지를 고치는 흐름은 미구현입니다.
- 5~7단계까지의 약점(서버 전용 키가 RLS를 우회하고 소유자 검사 코드가 방어선인 점, 호출 횟수 제한 없음, 화면이 실행 중 공개 키를 읽음, 판정기와 실제 접속 경로의 연결 미확인)은 그대로입니다.

## 7단계: 평소와 다른 접속은 다시 확인함 (8단계의 바탕)

- `src/decider.mjs`에 규칙 `step_up_required`를 더했습니다. `RULE_IDS`는 `['device_registered', 'step_up_required']`입니다. 6단계의 기기 규칙은 그대로 먼저 적용됩니다(미등록 기기는 항상 `deny`·`device_not_registered`).
- **다시 확인(`step_up`, 이유 코드 `step_up_required`)을 요구하는 조합**: 아래 세 가지가 **모두** 겹칠 때만입니다.
  1. 평소 없는 시각: `signals.hour`가 0~5시
  2. 처음 보는 네트워크: `signals.network`가 `unusual`
  3. 짧은 시간의 많은 읽기: 최근 5분(300초) 안의 `risk_signal` 사건 횟수 합계가 10 이상
  나머지 등록 기기 요청은 `allow`(`approved`)입니다. 한두 가지만 이상한 요청은 허용합니다.
- **지역(`signals.region`)은 읽지 않습니다.** 지역 하나만으로 차단하거나 다시 확인을 요구하지 않으며, 사유는 응답의 `reasonCode`(`step_up_required`)와 `ruleIds`에 남습니다.
- **다시 확인이 끝난 요청**은 `allow`입니다. 엔진이 준 `stepUp`이 `verified: true`(정확히 불리언 true)이고 `authAgeSeconds`가 0~900 사이 정수일 때만 인정합니다. 그 밖의 모양(문자열 `'true'`, 범위 밖 나이, 값 없음)은 계속 `step_up`입니다.
- **입력 검사(제작 1)**: 접속 정보는 `signals.source`가 `judge_fixture`인 심판의 가상 사건일 때만 읽습니다. 현재 실제 경로의 `source`는 `none`이라 실제 접속은 이 규칙에 걸리지 않고, `judge_fixture` 값을 실제 위치 증거로 취급하지 않습니다. `source`가 다르거나(`none`, `client`, 빈 값 등), `hour`가 0~23 정수가 아니거나, `network`가 문자열이 아니면 **정상값으로 채우지 않고 근거에서 뺍니다**(이상으로 세지 않음). 요청에 덧붙인 `role`·`identity`·`device`·`geo`·헤더는 읽지 않아 접속 정보로 승격되지 않습니다. 시험(`test/decider.test.mjs`)이 이를 확인합니다.
- 판정기가 읽는 요청 항목은 계약의 이름 중 `requestId`, `deviceRegistered`, `signals`, `recentEvents`, `stepUp`뿐입니다. 응답은 `schema`, `requestId`, `decision`, `reasonCode`, `ruleIds` 다섯 항목이고 함수 이름·인자는 그대로입니다.
- 기존 자료실 주소와 브라우저 화면은 바꾸지 않았습니다. (`aleph.config.json`의 `step`은 7단계 시점에 7이었고 8단계에서 8로 올렸습니다.)

### 확인 순서

1. `npm run decider:test` — 가상 요청 네 건. 정상 출력은 `통과 · 등록 기기의 정상 요청`(`allow`), `통과 · 미등록 기기의 가상 요청`(`deny`·`device_not_registered`), `통과 · 복합 이상 접속`(`step_up`·`step_up_required`), `통과 · 다시 확인한 복합 이상 접속`(`allow`)입니다.
2. `npm run fixture:7` — `정상 사건: allow`, `복합 이상 사건: step_up`이 나와야 합니다.
3. `npm run test:decider` — 출처가 다른 신호·모양이 틀린 값·지역만 이상한 요청이 이상으로 세어지지 않는지, 한두 가지만 이상하면 허용인지, 재확인 값의 모양별 결과를 확인합니다.

이 세 명령은 가상 요청 연습이며 **심판 판정이나 운영 반 엔진의 결과가 아닙니다.**

### 제작 3: 실제 재로그인 확인 (미실행)

- 계약(`docs/DECIDER_REQUEST.md`)에는 엔진이 요청에 넣어 주는 `stepUp: {verified, authAgeSeconds}`가 있고, 판정기는 그 값만 읽습니다. 토큰 원문은 판정기가 받지도 기록하지도 않습니다.
- 다만 **엔진이 실제 새 로그인 시각을 검증해 이 값을 채우는지, `step_up` 결정이 실제로 자료를 막고 새 로그인 뒤 요청을 다시 판정하는지는 이 저장소에서 확인하지 못했습니다.** 실제 경로의 `signals.source`가 `none`이라 실제 접속에서는 이 규칙이 발동하지 않습니다.
- 그래서 "다시 확인 전 자료 차단"과 "새 로그인 뒤 허용"의 실측은 **미실행**입니다. 계약이 준비된 환경(심판)에서만 시험할 수 있습니다.

### 7단계의 알려진 약점

- 규칙 조합과 기준값(0~5시, 사건 10회, 300초)은 학습용으로 정한 값입니다. 실제 사용자의 평소 패턴을 학습한 것이 아니고, `risk_signal`이 곧 '자료 읽기'라는 보장도 계약에 없습니다(가상 사건 모양을 따랐습니다).
- 세 가지가 모두 겹쳐야 하므로, 공격자가 시각이나 요청 속도를 조절해 한두 가지만 이상하게 만들면 이 규칙을 피할 수 있습니다.
- `step_up`은 엔진에 다시 확인을 요청하는 결정일 뿐이고, 실제 차단은 엔진이 합니다. 판정기가 `allow`를 돌려줘도 엔진의 앞선 신원·기기·경로 검사를 되돌리지 못합니다.
- 5·6단계까지의 약점(서버 전용 키가 RLS를 우회, 호출 횟수 제한 없음, 화면이 실행 중 공개 키를 읽음, 판정기와 실제 접속 경로의 연결 미확인)은 그대로입니다.

## 6단계: 등록한 기기만 자료실에 들어옴 (7단계의 바탕)

- `src/decider.mjs`의 `decide(request)`에 규칙 하나, `device_registered`를 더했습니다. 6단계 시점의 `RULE_IDS`는 `['device_registered']`뿐이었습니다(시작 틀의 `starter.deny`는 뺐습니다). 7단계에서 규칙이 하나 늘었습니다.
  - `request.deviceRegistered`가 정확히 `true`이면 `allow`(`approved`)입니다.
  - `false`이거나 값이 없거나 `'true'` 같은 다른 모양이면 `deny`(`device_not_registered`)입니다.
- 판정기가 읽는 요청 항목은 `requestId`와 `deviceRegistered` 둘뿐입니다. 계약(`docs/DECIDER_REQUEST.md`)에 없는 `request.role`, `request.identity`, `request.device`, `request.geo`는 읽지 않습니다. 응답은 `schema`, `requestId`, `decision`, `reasonCode`, `ruleIds` 다섯 항목이고 함수 이름·인자는 그대로입니다.
- 계약상 요청 항목 중 이번 규칙과 관련된 것: `subjectId`는 엔진이 만든 가명 주체 ID(사용자 번호와 직접 비교하지 않음), `deviceId`는 확인된 기기의 16자리 16진수 ID(개인키 아님), `deviceRegistered`는 기기 등록 여부입니다. 실제 릴레이는 미등록 기기를 판정기보다 먼저 막고, `false`는 심판의 가상 요청에서만 올 수 있다고 계약에 적혀 있습니다.
- 인증서·CA·서명 키·개인키는 만들지도 저장소에 넣지도 않았고, 이번 단계에는 설치할 접속 프로그램이 없습니다.
- 기존 자료실 주소(`/api/notes`, `/api/notes/:id`)와 브라우저 화면은 바꾸지 않았습니다. `aleph.config.json`의 `step`은 6이고, 빌드·점검 스크립트가 6단계를 받게만 고쳤습니다.

### 확인 순서

1. `npm run decider:test` — 가상 요청 두 건을 실행합니다. 정상 출력은 `통과 · 등록 기기의 정상 요청`과 `통과 · 미등록 기기의 가상 요청`입니다(전자는 `allow`, 후자는 `deny`·`device_not_registered`). 이 명령은 연습이며 **심판 판정이나 운영 반 엔진 결과가 아닙니다.**
2. `npm run test:decider` — 판정기가 `requestId`·`deviceRegistered`만 읽는지, 값이 없거나 이상한 모양이면 거부하는지, 모든 응답이 다섯 항목이고 `ruleIds`가 `RULE_IDS` 안에 있는지 확인합니다.
3. 등록된 내 기기에서 기존 화면에 로그인해 메모가 열리는지 직접 확인합니다.
4. 미등록 기기의 실제 공격은 심판이 맡습니다. 이 저장소의 시험은 가상 요청이며, 판정기가 실제 접속 경로에 연결돼 동작하는지는 여기서 확인하지 못했습니다.

`npm run fixture:7`은 7단계 연습이라 6단계 시점에는 실패하는 것이 정상이었고, 7단계에서 통과합니다.

### 6단계의 알려진 약점

- (6단계 시점) 이 규칙은 기기 등록 여부 하나만 봤습니다. 시각·네트워크·반복 시도·재인증은 7단계에서 더했습니다.
- 기기 등록 자체는 운영 반 엔진이 확인합니다. 판정기는 엔진이 준 `deviceRegistered` 값을 믿을 뿐이며, 그 연결은 이 저장소에서 확인하지 못했습니다.
- 5단계까지의 약점(서버 전용 키가 RLS를 우회하고 소유자 검사 코드가 방어선인 점, 호출 횟수 제한 없음, 화면이 실행 중 공개 키를 읽는 점)은 그대로입니다.

## 5단계: 자료 요청을 서버 한곳으로 모음 (6단계의 바탕)

- 브라우저는 메모를 서버 함수(`/api/notes`, `/api/notes/:id`)로만 읽고 고칩니다. `public/index.html`이 Supabase에 직접 부르는 것은 로그인(`signInWithPassword`, `signOut`, `onAuthStateChange`)뿐이고, 메모 테이블을 직접 읽거나 쓰는 호출(`.from(`, `/rest/v1`)은 **없음**을 확인했습니다. 그래서 5단계에서 화면 파일은 바꾸지 않았습니다.
- 서버 함수의 로그인·소유자 검사와 서버 전용 설정(`SUPABASE_SECRET_KEY`)은 그대로입니다.
- `aleph.config.json`의 `step`은 5이고 `originalApiUrl`은 원본 자료 주소(`https://<프로젝트>.supabase.co/rest/v1/study_notes`, 쿼리 없음)입니다. 빌드가 `/aleph.json`에도 이 값을 싣고, 같은 Supabase 프로젝트의 `study_notes` 경로가 아니면 실패합니다. 심판이 이 값을 어떻게 읽는지는 확인하지 못했고, `/aleph.json`에 싣는 것은 5단계 안내(원본 직접 요청은 공개 키로 확인)에서 추정한 선택입니다.
- DB 직접 권한 회수(제작 2)는 학습 DB에서 직접 실행하는 SQL로 제안했습니다. `study_notes`에서 `PUBLIC`·`anon`·`authenticated`의 모든 권한을 회수하는 내용이고 이 저장소에는 넣지 않았습니다. **적용 여부는 아직 확인되지 않았습니다.** 서버 함수는 서버 전용 키(`service_role`)로 접근하므로 영향이 없어야 하며, 적용 뒤 화면에서 A가 정상 동작하는지 다시 확인합니다. 4단계의 RLS 정책은 그대로 남아 있어도 직접 권한이 없으면 쓰이지 않습니다.
- `src/attack-check.mjs`의 5단계 점검: 비로그인 `/data.json`, `GET /api/notes`, `GET /api/notes/:id`와 함께, 배포의 `/aleph.json`에 공개된 공개 키로 `originalApiUrl`을 직접 불러 보는 점검(`direct_original_read`)을 실제로 요청해 상태 코드만 기록합니다. 키와 응답 본문은 기록하지 않습니다. A·B 로그인 교차 요청은 토큰이 필요해 **미실행**입니다.
- 다시 실행: `npm run test:notes`, `npm run test:r5`, `npm run build -- --local`

### 5단계의 알려진 약점

- 화면의 로그인은 Supabase 공개 키가 필요해, 브라우저가 실행 중에 `/aleph.json`의 `database.publishableKey`를 읽어 씁니다. `public/index.html` 파일 안에는 키가 적혀 있지 않지만, `/aleph.json`이 공개 키를 싣고 있고 브라우저 메모리에도 있습니다. 공개 키는 비밀이 아니며 권한 회수와 RLS가 직접 접근을 막는 구조입니다. 다만 "화면 코드에 공개 키가 없다"는 점검을 파일 내용 검색으로 하면 통과하고, 실행 중 요청까지 보면 통과하지 못할 수 있습니다.
- 권한 SQL을 적용하기 전에는 공개 키로 직접 접근할 수 있는지 이 저장소만으로는 알 수 없습니다.
- 서버 전용 키는 RLS를 우회하고, API의 소유자 검사 코드가 유일한 방어선이라는 점은 4단계와 같습니다.
- 호출 횟수 제한이 없고 비밀번호 정책·회원가입 제한은 Supabase 기본값입니다.
- 6단계 이후 변경 뒤에는 화면에서 A·B·비로그인 흐름을 다시 확인해야 합니다.

## 4단계: 로그인해도 내 자료만 보이게 함 (5단계의 바탕)

- 서버(`src/notes-api.mjs`)는 읽기·추가·수정·삭제 모두 **서버가 확인한 사용자 id와 행의 `owner_id`가 같을 때만** 처리합니다. 목록과 한 건 조회, 수정, 삭제의 DB 질의에 `owner_id = 내 id` 조건이 들어 있습니다. URL이나 요청 본문의 `owner_id`·`userId`는 읽지 않습니다.
- 수정은 기존 행이 본인 것일 때만 바뀌고, 저장하는 새 행의 `owner_id`도 본인 id로 고정합니다. 본문에 다른 `owner_id`를 넣어도 주인은 바뀌지 않습니다.
- 남의 메모를 읽거나 고치거나 지우려 하면 **404 `NOT_FOUND`**입니다. 없는 번호와 같은 응답이라 번호를 바꿔 보는 요청으로 남의 메모가 있는지도 알 수 없습니다. 응답 모양은 그대로입니다(한 건 `{id,title,body}`, 수정 본문 `{title,body}`).
- `owner_id`가 비어 있는 메모는 **아무에게도 보이지 않습니다**(기본 거부). 3단계에서는 이런 가상 메모가 로그인한 모두에게 보였습니다. 기존 가상 메모를 A에게 연결하려면 학습용 SQL(이메일이 들어가므로 이 저장소에 두지 않습니다)을 Supabase SQL Editor에서 직접 실행해야 합니다. 실행 전에는 목록이 비어 보이는 것이 정상입니다.
- (4단계 시점) `allowedRoutes`는 그대로 `/api/notes`(GET·POST)와 `/api/notes/:id`(GET·PUT·DELETE)였습니다. 8단계에서 메서드를 붙인 세 경로로 바뀌었습니다. `aleph.config.json`의 `step`은 4이고, 빌드(`scripts/deployment-identity.mjs`, `scripts/build-public.mjs`)와 `src/attack-check.mjs`가 step 4를 받습니다.
- `src/attack-check.mjs`의 4단계 점검: 비로그인 `/data.json`, 비로그인 `GET /api/notes`, 비로그인 `GET /api/notes/:id`(존재하지 않는 시험 번호)를 실제로 요청해 결과만 기록합니다. A·B 교차 요청(남의 번호로 읽기·수정·삭제)은 로그인 토큰이 필요해 **미실행**입니다. 그 부분은 화면에서 A와 B 창을 따로 열어 직접 확인합니다.
- DB 쪽 권한(제작 3): `study_notes`에서 `PUBLIC`·`anon`·`authenticated` 권한을 회수한 뒤 `authenticated`에 SELECT·INSERT·UPDATE·DELETE만 주고, 네 가지 모두 `auth.uid() = owner_id`인 행에만 허용하는 RLS 정책을 거는 SQL을 **제안**했습니다. 이 저장소에는 SQL을 넣지 않았고, **적용 여부는 아직 확인되지 않았습니다.** 실행한 뒤 `information_schema.role_table_grants`와 `has_table_privilege`로 `anon`에 권한이 없는지 직접 확인합니다.
- 다시 실행: `npm run test:notes`, `npm run test:r5`, `npm run build -- --local`

### 4단계의 알려진 약점

- 서버 함수는 **서버 전용 키**로 DB에 접근하고 이 키는 RLS를 우회합니다. 그래서 API의 소유자 검사 코드가 유일한 방어선이고, DB 권한(RLS)은 직접 Data API 접근에 대한 두 번째 방어입니다. 검사 코드에 빠진 경로가 생기면 그대로 뚫립니다.
- 남의 메모는 404로 숨기지만, 응답 시간이나 오류 형식 차이로 존재 여부를 추측하는 방법까지 막았다고 확인하지는 않았습니다.
- `/api/notes` 주소는 공개되어 있고(로그인 없이는 거부), 호출 횟수 제한이 없습니다. 비밀번호 정책·회원가입 제한은 Supabase 기본값입니다.
- 주인이 없는 행은 아무도 못 보기 때문에, 연결하지 않으면 메모가 사라진 것처럼 보입니다. 데이터는 DB에 그대로 있습니다.
- A·B 교차 요청의 실제 결과와 RLS 적용 결과는 이 저장소의 시험이 아니라 배포·DB에서 직접 확인해야 합니다. 시험은 가짜 저장소로 한 단위 시험입니다.
- 이후 단계(5단계 원본 API 연결 등)를 한 뒤에는 화면에서 A·B 흐름을 다시 확인해야 합니다.

## 3단계: 로그인과 메모 추가·수정·삭제 (4단계의 바탕)

- 화면(`/`)에서 이메일·비밀번호로 로그인·로그아웃합니다. 로그인은 Supabase Auth 공식 SDK(`@supabase/supabase-js`)로 하고, 실패하면 이유(맞지 않는 계정, 이메일 미확인, 시도 과다 등)를 화면에 보여 줍니다. 로그인 전에는 메모가 한 건도 보이지 않습니다.
- 로그인한 사람은 메모를 추가·수정·삭제할 수 있습니다. 화면은 로그인 토큰을 `Authorization: Bearer …` 헤더로 보냅니다.
- 서버 함수 `api/notes/index.js`(`GET`·`POST /api/notes`)와 `api/notes/[id].js`(`GET`·`PUT`·`DELETE /api/notes/:id`)는 공통 코드 `src/notes-api.mjs`를 씁니다. 토큰이 없거나 틀리면 HTML이 아니라 JSON 오류(`401 {"error":"UNAUTHORIZED",…}`)로 거부합니다.
- 토큰 확인은 시작 틀의 `src/verify-login.mjs`(수정하지 않음)로 합니다. 새 메모의 `owner_id`는 브라우저가 보낸 값이 아니라 **서버가 확인한 사용자 id**로 채웁니다. 요청 본문의 `owner_id`·`userId`·`role` 같은 값은 무시합니다.
- 로그인 발급자 정보는 `aleph.config.json`의 `identityProvider`(발급자 주소, audience, 공개 키 목록 주소)에 있고 비밀값은 없습니다. 허용 경로는 `allowedRoutes`(3단계 시점에는 `/api/notes`, `/api/notes/:id`, 8단계에서 메서드를 붙인 형식으로 바뀜)입니다. 빌드가 만드는 `/aleph.json`에도 두 값이 들어가며, 발급자가 `SUPABASE_URL`과 같은 프로젝트를 가리키지 않으면 빌드가 실패합니다.
- 환경변수(Vercel Project Settings > Environment Variables): `SUPABASE_URL`(경로 없는 `https://….supabase.co`), `SUPABASE_PUBLISHABLE_KEY`(공개 키), `SUPABASE_SECRET_KEY`(서버 전용, 브라우저에 절대 노출하지 않음). 넣거나 바꾼 뒤에는 다시 배포합니다.
- 시험 계정: Supabase 대시보드 Authentication > Users > Add user로 직접 만듭니다(비밀번호는 화면에서만 입력하고 어디에도 적지 않습니다).
- 다시 실행: `npm run test:notes`, `npm run test:r5`, `npm run build -- --local`
- 3단계 저장점: `aleph.config.json`의 `step`을 3으로 올렸고(4단계에서 4로 올림), `scripts/deployment-identity.mjs`·`scripts/build-public.mjs`·`src/attack-check.mjs`가 step 3을 받게 했습니다. `src/attack-check.mjs`는 비로그인 `/data.json`(메모 없음 확인)과 비로그인 `GET /api/notes`(401·403과 JSON 오류로 거부되는지)를 실제로 요청해 결과만 기록합니다. 정상 로그인(A)과 다른 사람(B)으로 보내는 점검은 토큰이 필요해 **미실행**입니다.

### 3단계 시점의 약점 (기록, 4단계에서 해소)

- **(4단계에서 막음) 메모의 주인을 확인하지 않았습니다.** 로그인한 B가 A의 메모 id를 알면 `GET`·`PUT`·`DELETE /api/notes/:id`로 읽고 고치고 지울 수 있었습니다.
- **(4단계에서 바뀜)** 목록은 `owner_id`가 비어 있는 가상 메모를 로그인한 누구에게나 보여 줬습니다.
- `/api/notes` 주소는 여전히 공개되어 있습니다. 로그인 없이는 거부할 뿐, 막는 것은 토큰 확인 하나입니다.
- 서버 전용 키는 RLS를 우회합니다. 제한은 서버 코드가 입력(제목 1~200자, 내용 5000자 이하)과 읽는 열을 검사하는 것뿐입니다.
- 호출 횟수 제한이 없고, 회원가입 제한·비밀번호 정책은 Supabase 기본값 그대로입니다.
- 호출 횟수 제한이 없는 점 등 나머지 약점은 4단계의 알려진 약점에 이어집니다.

## 2단계: 자료를 코드 밖으로 옮김 (3단계의 바탕)

- 가상 메모 네 건은 Supabase의 `public.study_notes` 테이블에 있습니다. 이 테이블은 RLS를 켜고 `anon`·`authenticated`에는 읽기 권한을 주지 않았습니다. 테이블 생성 SQL에는 메모 문장이 들어 있어 이 저장소에 커밋하지 않습니다.
- 2단계에서는 화면이 로그인 없이 `GET /api/notes`를 호출했고 서버 함수 `api/notes.js`가 `title`, `content`만 돌려줬습니다. 3단계에서 함수는 `api/notes/` 폴더로 옮겨 로그인을 요구합니다(위 참고).
- 서버 함수는 환경변수 `SUPABASE_URL`과 `SUPABASE_SECRET_KEY`를 읽습니다. Vercel의 Project Settings > Environment Variables에 직접 넣고, 넣은 뒤 다시 배포하세요. 비밀 키는 코드·Git·README·브라우저 파일·응답·로그에 넣지 않습니다. 환경변수가 없으면 함수는 500 `NOTES_NOT_CONFIGURED`만 돌려줍니다.
- `data.json`과 `public/data.json`의 `notes`는 비어 있고, 빌드(`scripts/build-public.mjs`)는 `notes`에 항목이 있으면 실패합니다. 그래서 `/data.json`에는 메모가 나오지 않습니다.
- 2단계 저장점에서는 `step`을 1로 두었습니다. 3단계에서 3으로 올렸습니다.
- 빌드가 만드는 `/aleph.json`에는 `database` 칸(Supabase 주소, 공개 키, 테이블 이름 `study_notes`)이 들어갑니다. 심판이 공개 키로 직접 요청해 보기 위한 값입니다. 값은 Vercel 환경변수 `SUPABASE_URL`(`https://….supabase.co`)과 `SUPABASE_PUBLISHABLE_KEY`(`sb_publishable_`로 시작하는 공개 키)에서 읽고, 하나라도 없거나 형식이 다르면 빌드가 실패합니다. 서버 전용 `SUPABASE_SECRET_KEY`는 이 파일에 절대 넣지 않으며, secret 키 모양의 값은 빌드가 거부합니다.
- 다시 실행: `npm run test:notes`, `npm run test:r5`, `npm run build -- --local`
- 저장점 「2단계」: `aleph.config.json`의 `repoUrl`과 `publicAppUrl`을 실제 저장소와 배포 주소로 채웠습니다(`judgeIssuer`는 그대로). 제출 묶음은 `npm run bundle`로 만들며, 커밋하지 않는 `bundle-notes.json`에 이번 단계에서 한 일을 적어 둬야 합니다. `bundle`은 실제 배포 주소로 요청을 보내므로 인터넷에 연결된 컴퓨터에서 실행합니다.

### 2단계 시점의 약점 (기록)

3단계에서 일부가 바뀌었습니다. 현재 약점은 위 '3단계의 알려진 약점'을 보세요.

- **(3단계에서 로그인 요구로 바뀜) 함수는 공개 주소였습니다.** `/api/notes`는 로그인 없이 누구나 호출해 메모를 받을 수 있습니다. 비밀 키는 서버에만 있어 새어 나가지 않지만, 함수 자체는 접근을 막지 않습니다. 로그인과 허용 경로는 3단계 이후에 추가합니다.
- 서버 전용 키는 RLS를 우회합니다. 지금의 한도는 함수가 읽는 열을 `title`, `content`로 제한하고 최대 100건만 돌려주는 것뿐입니다.
- 호출 횟수 제한이 없습니다. 반복 호출로 Supabase와 Vercel 사용량을 소모시킬 수 있습니다.
- 메모가 사용자별로 나뉘어 있지 않습니다. `owner_id`가 비어 있어, 호출한 사람이 누구든 같은 전체 목록(최대 100건)을 받습니다.

## 가상 메모 노출 확인 절차

가상 메모 문장은 이 저장소의 어떤 파일에도 적지 않습니다. 아래 절차는 문장 목록을 저장소 밖 임시 파일로 만들어 검색합니다.

**준비.** Supabase SQL Editor에서 `select content from public.study_notes order by id;`를 실행하고, 결과의 `content` 네 줄을 한 줄에 하나씩 `~/memo-sentences.txt`에 저장합니다. 파일은 저장소 밖에 두고 커밋하지 않으며, 확인이 끝나면 지웁니다. 빈 줄이 있으면 모든 줄이 일치한 것으로 나오니 빈 줄을 두지 않습니다.

**확인.** 세 가지를 각각 따로 실행하고 따로 기록합니다.

1. GitHub 최신 파일: `git fetch origin main` 뒤 `git grep -nF -f ~/memo-sentences.txt origin/main`. 통과 기준은 출력이 없는 것입니다.
2. 현재 배포 파일: `APP`에 배포 주소(`https://….vercel.app`)를 넣고 `for p in / /data.json /aleph.json; do printf '%s ' "$p"; curl -fsS "$APP$p" | grep -cF -f ~/memo-sentences.txt; done`을 실행합니다. 세 경로 모두 0이어야 통과입니다. `/aleph.json`의 `commit`이 1번에서 확인한 커밋과 다르면 새 배포가 아직 반영되지 않은 것이므로 통과로 치지 않습니다. `/api/notes`는 로그인한 사람에게 메모를 돌려주는 것이 정상이라 이 검색에서 제외하고, 위 '알려진 약점'에 따로 기록합니다.
3. 옛 기록(참고): `git grep -nF -f ~/memo-sentences.txt e3a3cd4`. 일치가 나오는 것이 현재 상태입니다.

**과거 노출은 해소되지 않았습니다.** 1번과 2번이 통과해도 "지금의 최신 파일과 현재 배포에는 없다"는 뜻일 뿐입니다. 옛 공개 커밋 `e3a3cd4`에 메모 문장이 남아 있고 저장소가 공개라 누구나 볼 수 있습니다. 이전 Vercel 배포도 삭제하기 전까지 그 시점의 파일을 계속 제공할 수 있습니다. 그래서 과거 노출이 해소됐다고 쓰지 않습니다. 커밋 이력 정리와 옛 배포 삭제는 이 단계에서 하지 않았습니다.

## 시작 틀의 자동 처리

`vercel.json`은 정적 결과물 `public`을 배포합니다. 빌드 명령 `npm run build`는 Vercel이 제공하는 GitHub 저장소 소유자·이름, 커밋 SHA, 배포 URL을 검증하고 `public/aleph.json`을 생성합니다. 이 값이 없으면 빌드가 실패하므로, 성공한 것처럼 빈 주소를 내보내지 않습니다. `aleph.json`의 내용만으로 저장소 소유권이나 방어 성공을 인정하지 않습니다. 심판이 공개 저장소의 실제 커밋과 배포된 자료를 따로 대조해야 합니다.

`aleph.config.json`의 `repoUrl`과 `publicAppUrl`은 시작 틀에서는 이전 제출 묶음 방식의 자리표시자였고, 1단계에서는 학생이 편집하지 않습니다. 이 저장소는 2단계 저장점에서 실제 주소로 채웠고, 3단계에서 `identityProvider`와 `allowedRoutes`를 더했습니다. 2단계 이후 코딩 도구가 필요한 설정과 보호 기능을 단계별로 작성합니다. `npm run bundle`과 `bundle-notes.json`도 1단계의 세 걸음에는 포함되지 않습니다.

로컬에서 가상 화면만 확인할 때는 `npm run build -- --local`을 사용합니다. 로컬 실행은 Vercel 배포나 심판 접수를 증명하지 않습니다. 저장소의 `src/attack-check.mjs`는 실제 배포가 된 뒤 `/data.json`을 비로그인으로 요청해 공개 가상 메모의 확인 표시를 읽습니다. 2단계 변경 뒤에는 `/data.json`에 메모가 없으므로 이 점검이 "확인 표시가 보이지 않음"으로 기록되는 것이 정상입니다. 3단계부터는 비로그인 `/api/notes` 점검이 함께 실행됩니다. 이 결과는 학생의 자기 점검이며 심판의 판정이 아닙니다.
